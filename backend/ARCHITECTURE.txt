GOOFFER BACKEND — АКТУАЛЬНАЯ АРХИТЕКТУРА
=========================================

Транспортный слой
  net/http ServeMux -> request-id/logger/recovery/CORS -> middleware авторизации
  -> обработчики -> отдельные DTO запросов и ответов.

Сценарии использования
  auth       регистрация аккаунта, пароли Argon2id, хешированные сессии
  profile    CRUD профилей с проверкой владельца и данными viewed_ads/own_ads
  generator  метрики за UTC-год -> сводка/карточки/достижения -> сохранение recap
  mission    выбор миссии владельцем и расчёт прогресса по последующим событиям
  carddefinition  CRUD правил дополнительных карточек, доступный администратору

Хранение данных
  PostgreSQL — единственный постоянный источник данных для аккаунтов, сессий,
  профилей, итогов, миссий и определений карточек. Встроенные SQL-миграции
  применяются транзакционно при запуске приложения. Миграция 009 назначает
  демонстрационный аккаунт nikita администратором.

  Redis — отказоустойчивый read-through-кэш только для сформированных итогов.
  Ошибка Redis не блокирует чтение или запись через PostgreSQL.

Источник данных для итогов
  User.Views (viewed_ads JSONB) и User.OwnAds (own_ads JSONB). Устаревшая модель
  actions/categories удаляется миграцией 008; репозитория и зависимости
  генератора для неё больше нет.

Административная граница
  Авторизация помещает account ID и is_admin в контекст запроса. Маршруты
  /api/admin/card-definitions дополнительно защищены RequireAdmin. Активные
  глобальные правила и правила конкретного профиля применяются при генерации,
  не меняя публичный контракт kind, который уже поддерживает frontend.

Граница безопасного экспорта
  Полный Recap -> ShareRecapResponse -> allowlist ShareRecapCardDTO. Endpoint
  share требует авторизации и доступен только владельцу. Публичные ссылки по
  токену не входят в MVP.

Направление зависимостей
  delivery -> сценарии и порты usecase -> domain
  реализации repository -> порты usecase и domain
  cmd/server связывает конкретные реализации.

Поток HTTP-запроса
  Клиент -> net/http ServeMux -> request-id/logger/recovery/CORS
  -> проверка cookie-сессии -> обработчик -> строгий DTO и валидация
  -> сценарий usecase -> порт repository -> PostgreSQL/Redis
  -> response DTO -> единый JSON-ответ.

  Административные маршруты после общей авторизации дополнительно проходят
  RequireAdmin. Ошибки преобразуются в публичный код и request_id; внутренние
  детали остаются только в структурированном server log.

Поток генерации итогов
  Профиль из PostgreSQL -> item-level события выбранного UTC-года
  -> buyer/seller/combined метрики -> summary
  -> встроенные карточки и графики -> активные правила CardDefinition
  -> достижения -> сохранение Recap в PostgreSQL -> обновление Redis-кэша.

  Повторная генерация заменяет итог того же профиля и года. Share-преобразование
  начинается только от сохранённого Recap и проходит через отдельный allowlist
  DTO, поэтому данные исходного профиля не попадают в экспорт напрямую.

Запуск, контракты, правила генерации, приватность, CI и известные ограничения
описаны в backend/README.md. HTTP-контракт находится в
backend/docs/swagger.yaml.
